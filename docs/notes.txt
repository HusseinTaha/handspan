Yes — ADB is probably the right foundation if your goal is a much better Windows ↔ Android file-transfer experience than Windows' built-in MTP/mobile-drive interface.

The key distinction is:

MTP (Media Transfer Protocol) → what Windows commonly uses when you plug in an Android phone and browse it like a drive. It's often slow, flaky, and has poor file-operation semantics.
ADB (Android Debug Bridge) → a command/transport protocol designed for communicating with Android devices over USB (and also Wi-Fi). It gives your app much more control.
Your app → can build a nice Explorer-like UI on top of ADB, without exposing the ugly MTP experience to the user.

ADB commands give you most of the primitives

For example:

Find connected devices.

Browse files.

Android → Windows.

Windows → Android.

And you can execute shell operations:

adb shell mkdir /sdcard/MyFolder
adb shell rm /sdcard/file.txt
adb shell mv /sdcard/a.txt /sdcard/b.txt


So yes, ADB can be the transport layer, while your application handles the user experience.

One important catch

ADB isn't quite a drop-in replacement for a filesystem.

For example, Android's /sdcard is generally emulated/shared storage, and modern Android versions have increasingly restrictive storage/security behavior. You should design your application around Android's storage model rather than assuming you have unrestricted access to the entire filesystem.

Also, the user normally needs to enable USB debugging and authorize your Windows computer on the phone.
